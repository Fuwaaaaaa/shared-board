プロジェクトの内容

何のためのアプリか

ログイン不要で、URL を共有するだけで使える共同編集ボードです。 ホワイトボード・カレンダー・リマインドの 3 つを 1 つのボードにまとめてあります。 利用者は最初に表示名を入れるだけで、メールアドレスもパスワードも要りません。

中核にあるのは 「付箋に書く → やることにする → 予定にする」 という流れです。 話し合いで出た内容がそのまま担当と期限を持った行動になり、出自 （source_note_id / source_event_id）を辿れます。

想定する規模

部活・サークル、家族、小さなお店、3〜5 人の仕事チーム。連絡網を作るほどではないが口頭では回らない集まり。

設計上の制約

常駐サーバーを持たない。アクセス制御はすべて PostgreSQL の RLS に寄せる。

置いていないもの

AI、ビデオ会議、ガントチャート、細かすぎるロール管理。用途をぼかさないため意図的に持たない。

ログインが無いことは、機能ではなく前提です。 匿名サインインで得た auth.uid() だけが本人を示す唯一の手がかりなので、 「誰が何をしたか」の記録（📣 更新タブ）と、参加の承認・権限の管理が、 他のアプリより重い役割を担っています。

データの持ち方

なぜこの形なのか

テーブルは 27 個。rooms を頂点に、中身は on delete cascade でぶら下がります。 主なものは notes / strokes / images / frames / connectors / attachments（ボード）、 events / event_overrides（カレンダー）、todos（リマインド）、 comments / activities / room_members（共有まわり）です。

覚えておきたい 4 つ

  • アクセス制御は全部 RLS。 画面側のチェックは親切のためのもので、 本当の防御は PostgreSQL にあります。INSERT には author_id = auth.uid() の条件が付くので、 他人の行をコピーして入れ直すときは作者を自分に差し替える必要があります。
  • 削除はゴミ箱行き。 deleted_at を立てるだけで、30 日は戻せます。 useWithoutDeleted が rows と trash に分けます。 comments もこの形ですが、戻せる人だけが違います—— 消す操作がモデレーションなので、消した本人（deleted_by）か オーナーだけ。判定はサーバー側（tg_comment_trash_guard）です。 strokes は列を持ちますが、2 つだけ流儀が違います—— 購読の時点でゴミ箱の行を外す（useRealtimeTable の skipDeleted。points が重いので全員に配らない）ため trash には載らず、ゴミ箱の中身は TrashModal が 開いたときに取りに行きます。もう 1 つは件数の上限がゴミ箱の行も数えること （tg_limit_rows_per_room の 'yield'。天井では古い行が席を譲ります）。
  • ボードを跨ぐ画面は、ボードごとに問い合わせない。 ホームの「自分の番」（MyOverview）は、やること・予定・ 「この回だけ」の 3 本だけを引きます。room_id では絞らず、 どのボードの行が返るかは RLS に任せます——参加ボードが 30 個あっても 3 本のままです。 繰り返しの展開は SQL でやらずに画面側でします （規則の写しを 3 つめにしないため。いまは画面と Edge Function が _shared/recurrence.ts を共有しています）。
  • 暦は Asia/Tokyo 固定。 Intl を使わず UTC に +9 時間して計算します。 実行環境のタイムゾーン設定に左右されないためで、テストでも TZ=America/New_York にして結果が変わらないことを確かめています。
  • 繰り返しの例外は別テーブル。 event_overrides が 「この回だけ変更・削除」を持ちます。.ics では RECURRENCE-ID / EXDATE に対応します。回の同定キーは occurrence_date（元の回の JST 開始日）で、これは 「1 予定につき 1 日 1 回しか出現しない」ことが前提です。曜日指定を足しても その前提は変わりません（毎週×曜日は各曜日が週 1 回、毎月 第 n 曜日は月 1 回）。

オフラインの送信箱

つながっていないあいだの書き込みは、行ごとに 1 件だけ IndexedDB にためて、 つながったら送ります（src/lib/writeQueue.ts）。 操作の記録を再生するのではなく、行ごとの最終状態だけを持ちます。 作って 12 回直した付箋は INSERT 1 回になり、作ってすぐ取り消したものは 1 件も送りません。件数の上限（tg_limit_rows_per_room）が見るのも、 畳んだあとの数です。

これが成り立つのは、アプリが行の id をクライアントで作っているから （crypto.randomUUID）。ふつうオフラインのキューを難しくするのは 「あとから決まる id をどう差し替えるか」ですが、ここではその問題が最初からありません。 主キーの重複（23505 で details に Key (id)=）を 成功として扱えるので、2 つのタブが同時に送っても壊れません。

いちばん間違えやすいのはリロードを跨ぐことです。 useRealtimeTable の保留（hold）はメモリ上にあり、購読しなおすたびに 作り直されます。送信箱から保留を張り直す仕組みが無いと、まだ送れていない行は リロードした瞬間に「サーバーが知らない行」として消えます——画面上は何ごともなく 消えるので、目で見ても気づけません（e2e/offline.spec.ts が見ています）。

数え方を 2 つに分ける

送る側は navigator.onLine を見ていません。つながっているつもりで 死んでいる回線（キャプティブポータル、不安定なモバイル）が普通にあるので、 フラグではなく「送れなかったこと」そのものを見ます。

そのぶん、届かなかった回数を「試した回数」に数えてはいけません。 数えてしまうと、ただ圏外にいるだけで打ち切りの上限（MAX_ATTEMPTS）に達し、 1+2+5+15+60+300+300 秒 ≒ 11 分で送信箱が全件 「何度か試しましたが送れませんでした」に落ちます。 「つながったら送る」という約束が、そこで果たせなくなります。 いまは transportAttempts を別に持ち、様子見の間隔だけを伸ばします （判断は nextRetryState）。回線が戻ったときは、その待ち時間を捨てて すぐ送ります——待つ理由は「届かない相手を叩き続けない」ためで、 圏外を抜けた瞬間まで持ち越す意味がないからです。

送っている最中の書き足しを守る

送るのは flush が始めた時点の写しです。往復のあいだに同じ行へ 書き足されたぶんは、その写しに入っていません。key だけを見て消すと、 その書き足しごと消えます。そこで、ためるたびに増える rev を比べ、 動いていたら捨てずに送り直す側へ回します（afterSend）。

ただし「作成」のまま送り直すと、こんどは主キーの重複になり 「前回の送信が実は通っていた」として捨てられ、やはり書き足しが消えます。 行はもうサーバーにあるので、更新に変えて送ります。

ためる相手と、見せる範囲

ためられるのは notes / events / todos / comments の 4 表です。1 件ずつの書き換え（patch）だけでなく、 まとめての変更（patchMany）も同じ経路に載ります—— 載せないでいると「本文の書き換えはためられるのに、ゴミ箱へ入れるのはその場で失敗する」 という食い違いが、同じ画面の中で起きます。

送信箱は端末にひとつで、全ボード分が同じ場所に入ります。 画面に出すときはいま開いているボードで絞ります。絞らないと、別のボードの未送信が ヘッダーの件数に混ざり、探しても見つからない数になります。 隠したままにもしません——別のボードにためた件数は送信箱の中に出し、 まとめてテキストに落とす道も残してあります。

共同編集のしくみ

useRealtimeTable が Supabase Realtime を購読し、 useOptimisticTable が「先に画面へ出して、失敗したら戻す」を担います。 本文とタグの変更だけ updated_at による楽観ロックが掛かり、 衝突すると「他の人が先に変更しました」と出して最新に戻します。 位置や色の変更にはロックを掛けません（掛けると譲り合いで動かなくなるため）。

右クリックメニュー

触りたいものの上で右クリックすると、そこでできることだけが出ます。 付箋・画像・フレームのタイトルバー・線・ファイル・何もない場所で、中身が変わります。

右クリックでしかできない操作はありません。 同じ内容に 3 通りの行き方を用意しています —— 右クリック（最速）、ツールバーの「⋯」（通常）、キーボード（慣れた人向け）。 スマホでは付箋の一覧表示に切り替わり、各行の 「⋮」 が同じ役目を持ちます。 キーボードからは Shift+F10 で開けます。

カレンダー

  • 月 / 週 / 日 / 一覧を切り替え。週表示と日表示には時間軸があります
  • ドラッグで移動。週表示では端をつまんで長さを変えられます
  • 繰り返しは 毎日 / 毎週 / 毎月 / 毎年。毎週は曜日を複数選べ、毎月は「第 2 火曜」のような曜日指定もできます。終了日も指定できます
  • 定例を 「この回だけ」 動かす・休むことができます（変えた回には ✏️ が付きます）
  • 日本の祝日は内部で計算します（外部通信なし）

リマインド

  • 期限で 期限切れ / 今日 / 3日以内 / それ以降 / 期限なし / 完了 に自動で分かれます
  • 担当者・サブタスク・繰り返し・コメントを持てます
  • 一覧とカンバンを切り替えられます

共有と権限

  • 入り方は リンク公開 / 合言葉つき / 承認制 の 3 つ
  • 配ったあとでも 新規参加の停止・人数上限・期限・リンクの作り直し ができます
  • 参加者ごとに 閲覧のみ / 編集できる。閲覧のみでもコメントと投票はできます
  • ボードを終了すると、中身は読めるまま書き込みだけ止まります。あとから再開できます

npm run lintESLint（数秒で終わる）

環境変数

.env.local に置きます。雛形は .env.example です。

  • VITE_SUPABASE_URL / VITE_SUPABASE_ANON_KEY — 必須
  • VITE_VAPID_PUBLIC_KEY — プッシュ通知を使う場合
  • VITE_TURNSTILE_SITE_KEY — 参加申請の bot 対策を使う場合
  • VITE_LAN=1 — 同じ LAN の別端末から見たいときだけ

VITE_LAN=1 は既定で外してあります。 開発サーバーそのものが攻撃面になるためです（同梱の esbuild には、 開発サーバーが任意のファイルを読み出せてしまう既知の問題があります）。 またこのとき http:// になるので、 navigator.clipboard が使えない点にも注意してください。

データベースの更新

supabase/schema.sql を Supabase の SQL Editor に貼って実行します。 冪等なので何度実行しても同じ状態になります。列を足すときは alter table ... add column if not exists の形で末尾に追記します。

引き継ぐ人へ

知らないと踏む落とし穴

  • ボードは transform: scale() の中にあります。 transform は position: fixed の基準になるため、 メニューなど画面に固定したいものをこの中に置くと、 倍率で拡大縮小されて位置もずれます。ボードの外に置いてください。
  • ダークモードに dark: は使いません。 src/index.css が Tailwind のカラー変数そのものを反転させます。 bg-white text-slate-800 と普通に書けば両方に対応します。 逆に bg-slate-800 と書くと、ダークで白くなって意図が壊れます。
  • useStableHandlers はキーの集合が初回で固定されます。 条件でハンドラを出し分けず、関数の中で分岐してください。
  • ドラッグ中に onLocalChange で書き換えたら、確定前に元の値へ戻してください。 親の commit* は「いま保持している行」を取り消しの戻り先にするので、 書き換えたまま確定すると Ctrl+Z が何もしないエントリになります。
  • キーボードの Ctrl 系は if (e.ctrlKey || e.metaKey || e.altKey) return より上に書いてください。 下に書くと届きません（WhiteboardTab.tsx のキーハンドラ）。
  • getRow() はゴミ箱の行も返します。 生きている行だけを見たいときは rows を使ってください。
  • 判断のあるところは src/lib/ の純粋関数へ押し出してください。 コンポーネントのテスト（*.test.tsx・jsdom）もブラウザのテスト （e2e/・Playwright）も書けるようになりましたが、どちらも遅く、 壊れやすく、落ちたときに原因が読み取りにくいのは変わりません。 そこでしか確かめられないことに絞ってください。
  • Supabase のエラーは Error のインスタンスではありません。 e instanceof Error ? e.message : String(e) と書くと、 サーバーが理由を返しているのに画面には [object Object] と出ます。 src/lib/errorMessage.ts の messageOf() を使ってください。
  • 権限は「名簿にどう載っているか」を、ボードの公開設定より先に見ます。 逆にすると、リンク公開のボードでアクセスを取り消された人が 「まだ来ていない人」に混ざり、そのまま入り直せてしまいます （useRoomAccess の判定の順番）。
  • 参加者になる道は request_access だけです。 却下された人が承認待ちに戻るときも、そこを通します。 room_members を直接いじれると、受付停止・参加期限・人数上限・ 合言葉の判定をすり抜けて列に並べてしまうためです。 tg_guard_member_update は request_access が置いた 使い捨ての目印（app.reapply_member）が指す行の更新しか通さず、 room_members_delete は自分の行でも status = 'approved'（＝退出）のときだけ許します。
  • 門番は「どの操作を見ているか」まで確かめてください。 これまで見つかった穴は、どれも同じ形でした——ポリシーやトリガーが INSERT だけ、あるいは UPDATE だけを見ていて、残りの操作が素通し。 rls.test.sql の最後の節が、ポリシー・トリガー・外から呼べる関数の 一覧を控えていて、増減すると落ちます。落ちたら、まず その増減が意図したものかを確かめてから控えを直してください。 順番を逆にすると、この節は何も守らなくなります。
  • タブとモーダルは React.lazy で分けて読み込んでいます。 src/pages/RoomPage.tsx で静的に import し直すと、 そのぶんが初回の読み込みに戻ります（画面は動くので気づけません）。 型だけ要るときは import type にしてください。 効いているかは npm run build の出力で、 WhiteboardTab-*.js などが別ファイルとして出ているかを見ます。
  • 控えの大きさの上限も 2 か所にあります。 src/lib/snapshot.ts の PAYLOAD_LIMIT と、 supabase/schema.sql の v_limits の snapshots.payload。理由は合言葉と同じです。
  • 合言葉の最短の長さは 2 か所にあります。 src/lib/access.ts の MIN_PIN_LENGTH と、 supabase/schema.sql の set_join_pin。 画面側にも持たせているのは、押してから断られるのを避けるためです。 変えるときは両方そろえてください。
  • 繰り返しの規則は 3 か所にあります。 supabase/functions/_shared/recurrence.ts の normalizeRule（間隔の上限 MAX_INTERVAL を含む）と、 supabase/schema.sql の events_recurrence_days_check ・ events_recurrence_interval_check。合言葉の長さと同じ理由で、 画面側にも同じ決まりを持たせています。変えるときは全部そろえてください。
  • ドラッグの確定は、コンポーネントのテストで守っています。 「確定前に元の値へ戻す」を忘れると画面上は正常に見え、 Ctrl+Z が黙って効かなくなるだけなので、 目で見ても気づけません（src/pages/tabs/__tests__/）。

いまの既知の課題

項目内容
外部カレンダーの RRULE FREQ / INTERVAL / COUNT / UNTIL / RDATE / EXDATE に加えて、 BYDAY（2TU のような序数つきを含む）・ BYSETPOS・WKST・ BYMONTH・BYMONTHDAY（-1 は月末）まで読みます。 これで祝日カレンダーの FREQ=YEARLY;BYMONTH=12;BYMONTHDAY=25 や、 「毎月 1 日と 15 日」「毎月の月末」「11 月の第 4 木曜」が正しい日に出ます。
まだ読まないのは BYWEEKNO / BYYEARDAY / BYHOUR / BYMINUTE / BYSECOND です。 これらは無かったことにはしません。見つけたら繰り返しの展開そのものをやめ、 DTSTART の 1 回だけを出して、購読先の一行と予定の ⚠ で断ります。
無視して DTSTART の日付で繰り返すと、出ないより悪い 「もっともらしい間違った予定」になるからです。 FREQ=YEARLY;BYYEARDAY=100 を「毎年 DTSTART の日」と読むと、 100 日目とは何の関係もない日に、正しそうな顔をした予定が毎年並びます。 見ている人には間違いだと分かりません。 カレンダーとしては間違った日に出すより、出さずに断るほうがましです。 読めない FREQ も同じ扱いにしています。 どれも一般に配られている .ics ではほとんど見ないので、 実物に当たってから足す方針です。
同じ名前でも FREQ によって「回を増やす」ときと「絞り込む」ときがあり （BYMONTH は YEARLY でだけ増やす）、 そこを取り違えると回数が合わなくなります。 書き出す側も INTERVAL（「n 回ごと」）を出すようになりました
お知らせの流量 同じ人あてに、重要さで分けた2 つの枠があります （tg_throttle_notifications）。@メンション・担当の指名・参加申請・ 参加の可否は毎分 20 件、付箋からの変換は毎分 10 件です。 枠が分かれているので、付箋をまとめて変換したときの通知が @メンションを押し出すことはありません。 超えた分は例外にはしません——お知らせを出せなかったことで、 出そうとした操作（付箋を書く、コメントする）まで失敗させないためです。 ただし捨てもしません。「ほかに N 件」という 1 行にまとめ、 件数を folded_count に足していきます（行は 1 分に 1 つしか増えません）。 数えるのは差出人ではなく宛先。notifications は差出人の id を 持っておらず、困るのは受け取る側だからです。 入れる条件が can_edit_room ではなく can_access_room なので、 閲覧だけの人でも参加者あてに書けます。send-reminders が未読を Web Push に変えるため、止めないと端末の通知を好きなだけ鳴らせてしまいます
知らない TZID 名前が Intl で引けるなら、本物の tz データで読みます（夏時間も込み）。 引けない名前（Outlook の "Customized Time Zone" など）は、 VTIMEZONE に書かれた切り替えの規則そのもの （FREQ=YEARLY;BYMONTH=3;BYDAY=-1SU の形）を展開して、 「いつ何分ずれるか」の一覧にしてから読みます。
以前は STANDARD の TZOFFSETTO を 1 つ拾って 一年中そのずれで通していたので、夏時間のある地域では半年ぶん 1 時間ずれていました。 貼った人からは「夏のあいだだけ 1 時間早く出る」という形で見え、理由が分かりません。
規則が読めなかったときだけ、これまでどおり固定のずれに落ちます。 起こす範囲は 1970〜2100 年で、その外側は端のずれで通します （src/lib/icsParse.ts の parseVTimezones）
毎月 31 日の .ics 丸めた回を RDATE で補っていますが、終わりの無い繰り返しでは 3 年ぶんで区切ります。それより先は書き出し直しが要ります
オフラインでためられるもの 付箋・予定・やること・コメントの文字だけです。手描き・画像・ファイル・ 投票はためません。画像とファイルは実体の置き場と行の作成が一度に決まらないため、 置こうとした時点で断ります。ためた場所はその端末の中だけで、 別の端末には引き継がれません
控えの大きさ 手描きの多いボードは payload の 3MB に当たって保存できません。 上限を握っているのは strokes の points です。 押す前に断るようにしてありますが、根本は変えていません
カレンダーの購読 URL 作り直すか止めるまで有効な「読み取りの権限」です。 revoke_all_members（全員を外す）では止まりません — 別の権限なので、別の操作で切る作りにしています。 共有画面の文面でそう伝え、発行と停止は 📣 更新タブに残します
ボード設定の反映 名前の変更・終了・リンクの作り直しは、presence:<roomId> への 合図で他の人に伝えます。送り手のチャンネルが繋がっていなければ送られないので、 取りこぼすと反映が最大 60 秒（保険の取り直しの間隔）遅れます。 ホーム画面からの終了は合図を出さないので、いつも保険頼みです。 サーバー側は常に正しく拒むため、遅れるのは画面の見た目だけです
CI が見ていないもの push すると lint・型・単体・Edge Function（Deno）・pgTAP・Playwright が 自動で回ります。Edge Function は fetch を差し替えて handler を直に呼ぶので、supabase start は要りません （supabase/functions/tests/）。ブラウザは Chromium が全部、 Firefox と WebKit は @smoke を付けた 2 件だけです。 残っているのはデプロイの自動化と、 スマホの画面幅で崩れないかを見るテストです （WebKit は engine の違いだけを見ていて、画面は Desktop の幅のままです）
