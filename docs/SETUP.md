## 1. Supabase プロジェクトを作る

1. <https://supabase.com> にサインアップ（GitHub アカウントでログインできます）
2. **New project** をクリック
3. 入力するもの
   - **Name**: 好きな名前（例 `minna-no-board`）
   - **Database Password**: 自動生成でよいですが、控えておいてください
   - **Region**: `Northeast Asia (Tokyo)` を選ぶと日本からの通信が速くなります
4. **Create new project** → プロビジョニング完了まで 1〜2 分待ちます

無料プランで問題ありません。

---

## 2. データベースを作る（SQL を 1 回流すだけ）

1. 左メニューの **SQL Editor** を開く
2. **New query** をクリック
3. このリポジトリの `supabase/schema.sql` を**すべてコピーして貼り付け**
4. 右下の **Run** をクリック

`Success. No rows returned` と出れば完了です。

このスクリプトは何度実行しても同じ状態になります。**既存のデータは消えません**。
あとから機能を追加したときも、同じファイルを貼り直して実行すれば追いつきます。

> 作られるもの: ボードとその中身のテーブル（rooms / room_members / notes / strokes /
> events / event_overrides / todos / images / comments など）、RLS ポリシー、
> 参加・共有まわりの RPC（`get_room_preview` / `request_access` / `rotate_room_slug` /
> `rotate_owner_token` / `set_join_pin` / `claim_owner` / `revoke_all_members` /
> `delete_my_account`）、リアルタイム配信の設定、画像用ストレージバケット。

最後に次のような行が出ていれば、画像機能まで含めて設定できています。

```
NOTICE:  画像・ファイル用ストレージの設定が完了しました。
```

代わりに `WARNING: ストレージの設定をスキップしました` と出た場合は、
DB 本体は問題なく作られています。画像機能だけ
[画像アップロードの設定](#画像アップロードの設定) の手順で追加してください。

## 3. 匿名サインインを有効にする

このサイトは「表示名を入力するだけ」で使えますが、裏側では Supabase の匿名サインインで
ブラウザごとの ID を発行しています。この ID があるおかげで、
「誰がこのボードのオーナーか」「承認済みか」をサーバー側（RLS）で判定できます。

1. 左メニューの **Authentication** → **Sign In / Providers**
2. **Anonymous sign-ins** を **Enabled** に切り替えて保存

> ここを有効にし忘れると、アプリ起動時に「接続できませんでした」と表示されます。

### 端末の引き継ぎを使う場合（任意）

ホーム画面の 📱 から、いまの「自分」にメールアドレスを結びつけられます。
別のパソコンやスマホでも同じ自分として入れるようになり、
参加しているボードや作ったものがそのまま引き継がれます（参加者 ID が変わらないため）。

使うには **Authentication → Sign In / Providers → Email** を **Enabled** にしてください。
確認メールとログイン用リンクの送信に使います。設定しなくても、
ボードの機能はすべてこれまでどおり動きます。

## 4. 接続情報をローカルに設定する

1. 左メニューの **Project Settings** → **API** を開く
2. 次の 2 つをコピー
   - **Project URL**
   - **Project API keys** の **anon / public** キー
3. プロジェクト直下の `.env.example` を `.env.local` という名前でコピーし、値を貼り付け

```env
VITE_SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

> **anon key はブラウザに配布される公開鍵です。** 秘密ではありません。
> データを守っているのは RLS（行レベルセキュリティ）のポリシーです。
> ただし **service_role キーは絶対にここへ書かないでください**。RLS を全部無視できてしまいます。

- 表示名を入力 → ホーム画面

## 画像アップロードの設定

`schema.sql` の実行時に「画像用ストレージの設定をスキップしました」と出た場合だけ、
以下を手動で行ってください（出ていなければ何もしなくて大丈夫です）。

プロジェクトによっては `storage` スキーマへの権限が制限されていて、
SQL からバケットとポリシーを作れないことがあります。

### 1. バケットを作る

1. 左メニューの **Storage** → **New bucket**
2. **Name**: `board-images`
3. **Public bucket**: **オフのまま**（リンクだけでは入れないボードの画像を守るため重要です）
4. **Save**

### 2. ポリシーを作る

**Storage** → **Policies** → `board-images` の **New policy** → **For full customization** で、
次の 3 つを作ります。いずれも対象ロールは `authenticated` です。

| 操作 | ポリシー名 | 条件（USING / WITH CHECK） |
| --- | --- | --- |
| SELECT | `board_images_select` | `bucket_id = 'board-images' and public.can_access_room(public.storage_room_id(name))` |
| INSERT | `board_images_insert` | `bucket_id = 'board-images' and public.can_edit_room(public.storage_room_id(name))` |
| DELETE | `board_images_delete` | `bucket_id = 'board-images' and public.can_edit_room(public.storage_room_id(name))` |

> **読むのは `can_access_room`、置く・消すのは `can_edit_room` です。**
> 3 つとも `can_access_room` にしてしまうと、「閲覧のみ」の参加者や
> 終了したボードでも画像を貼ったり消したりできてしまいます
> （下の「動作確認チェックリスト」で確かめられます）。

`can_access_room` / `can_edit_room` / `storage_room_id` は `schema.sql` が作成済みの関数です。
ファイルは `<ボードのID>/<ランダムな名前>.png` というパスに保存され、
先頭のフォルダ名がそのままアクセス判定に使われます。

### 3. 添付ファイル用のバケットも作る

画像以外（PDF など）を貼れるようにするためのバケットです。作らないと、
ボードへのファイルの貼り付けだけが黙って失敗します。

1. **New bucket** → **Name**: `board-files`
2. **Public bucket**: **オフのまま**
3. **Additional configuration** で次を設定
   - **File size limit**: `10 MB`
   - **Allowed MIME types**: 下の一覧（`schema.sql` と同じもの）

```
application/pdf, application/octet-stream, application/zip, application/json,
text/plain, text/csv, text/markdown, text/calendar,
image/png, image/jpeg, image/gif, image/webp,
application/msword,
application/vnd.openxmlformats-officedocument.wordprocessingml.document,
application/vnd.ms-excel,
application/vnd.openxmlformats-officedocument.spreadsheetml.sheet,
application/vnd.ms-powerpoint,
application/vnd.openxmlformats-officedocument.presentationml.presentation
```

> **種類を絞るのは飾りではありません。** Content-Type はアップロードする側が
> 自由に指定できるので、`text/html` や `image/svg+xml` を置けてしまうと、
> 署名付き URL を開いた人のブラウザで `<プロジェクト>.supabase.co` のオリジンとして
> 任意の JavaScript が動きます（利用者が信頼しているドメイン上でのフィッシングに使えます）。
> 画面側も添付の署名 URL は「必ずダウンロードになる」形で発行していますが、
> ここでも絞って二重にしておきます。

ポリシーは画像と同じ形で、バケット名だけ差し替えた 3 つを作ります。

| 操作 | ポリシー名 | 条件（USING / WITH CHECK） |
| --- | --- | --- |
| SELECT | `board_files_select` | `bucket_id = 'board-files' and public.can_access_room(public.storage_room_id(name))` |
| INSERT | `board_files_insert` | `bucket_id = 'board-files' and public.can_edit_room(public.storage_room_id(name))` |
| DELETE | `board_files_delete` | `bucket_id = 'board-files' and public.can_edit_room(public.storage_room_id(name))` |

## プッシュ通知（任意）

**タブを開いている間のブラウザ通知は、ここを設定しなくても動きます。**
「タブを閉じていても通知を受け取りたい」場合だけ、以下を設定してください。
Supabase CLI が必要です。

### 1. VAPID 鍵を作る

Web プッシュには、送信者を示す鍵ペア（VAPID 鍵）が要ります。

```bash
npx web-push generate-vapid-keys
```

`Public Key` と `Private Key` が表示されます。

### 2. 鍵を設定する

**公開鍵**はブラウザ側で使うので `.env.local` に入れます。

```env
VITE_VAPID_PUBLIC_KEY=BN...（Public Key）
```

**秘密鍵**はサーバー側だけで使います。ブラウザには絶対に渡しません。

Supabase CLI は **このリポジトリの devDependency** です。`npm install` を済ませてあれば、
`npx supabase ...` で package.json に固定した版（2.117.0）が動きます。
グローバルに入れたものを使うと、CI と違う版で動いていても誰も気づけません。

```bash
npx supabase login
npx supabase link --project-ref <PROJECT_REF>

npx supabase secrets set \
  VAPID_PUBLIC_KEY=BN...          \
  VAPID_PRIVATE_KEY=...           \
  VAPID_SUBJECT=mailto:you@example.com \
  SITE_URL=https://your-app.vercel.app
```

### 3. 送信用の関数をデプロイする

```bash
npx supabase functions deploy send-reminders
npx supabase functions deploy purge-storage
```

> **`--no-verify-jwt` は付けません。** JWT を検証するかどうかは
> `supabase/config.toml` に関数ごとに書いてあります。コマンドの付け忘れ・付けすぎで
> 設定が変わってしまわないよう、リポジトリ側で固定してあります。
>
> この 2 つはゲートウェイでの検証をしない設定なので、インターネットのどこからでも
> URL に到達できます。守っているのは関数の中の合言葉（`CRON_SHARED_SECRET`）だけです。
> 次の手順で必ず設定してください。設定しないと、関数は誰の呼び出しも受け付けません
> （開けっ放しにはならない代わりに、通知も掃除も動きません）。

### 4. 定期実行を設定する

`supabase/cron.sql` を開き、`<PROJECT_REF>` を自分の値に置き換えてから、
SQL Editor で実行します。1 分おきに関数が呼ばれるようになります。

**service_role キーはここには書きません。** Edge Function を呼ぶときの合言葉は
この SQL が自動生成して Vault に保存します。以前は service_role キーそのものを
毎分ヘッダで送っていましたが、pg_net は送信前のリクエストをヘッダごと DB のテーブル
（`net.http_request_queue`）に積むため、鍵が平文で DB に残っていました。

実行したら、生成された合言葉を Edge Function 側にも同じ値で設定します。

```bash
# SQL Editor で値を確認
#   select decrypted_secret from vault.decrypted_secrets where name = 'cron_shared_secret';

npx supabase secrets set CRON_SHARED_SECRET=<上で表示された値>
```

同時に「送信済み記録を 14 日で掃除」「変更履歴を 90 日で掃除」も設定されます。

> **なぜ service_role キーを使わないのか。**
> pg_net は送信前のリクエストを `net.http_request_queue` にいったん積みます。
> `headers` 列もそのまま入るので、service_role キーを毎分流していると、
> そのキーが平文で DB のテーブルに現れ続けることになります。
> しかも Supabase の既定では、このテーブルは `authenticated` から読める状態です。
>
> ```sql
> select has_table_privilege('authenticated', 'net.http_request_queue', 'SELECT');
> ```
>
> ここが `true` でも慌てなくて大丈夫です。権限を付けたのは `supabase_admin` なので、
> SQL Editor（`postgres` として動きます）からは剥がせません（`revoke` は黙って
> 何もしません）。PostgREST は `net` スキーマを公開しないため、ブラウザから
> 読む経路もありません。それでも「万一 DB に直接つながれたときに何が漏れるか」を
> 小さくしておきたいので、流すものを **service_role キーではなく専用の合言葉**に
> してあります。漏れても、その 2 つの関数を叩けるだけです。

### 5. ブラウザ側で受け取りを ON にする

Vercel の環境変数にも `VITE_VAPID_PUBLIC_KEY` を追加して再デプロイし、
サイトのリマインドタブで「📲 受け取る」を押します。

> **HTTPS が必須です。** `localhost` は例外的に動きますが、
> LAN 内の `http://192.168.x.x` では Service Worker が登録できません。

## CAPTCHA（任意）

匿名サインインは誰でも何度でも呼べます。放っておくと `auth.users` を機械的に
増やされたり、合言葉の総当たりに新しい ID を使い回されたりします。
Cloudflare Turnstile を有効にすると、サインインの前にそれを通します。

**合言葉つきのボードを配る予定があるなら、設定をおすすめします。**
合言葉の試行回数はボード全体でも数えていますが、その枠を厳しくすると
「正しい合言葉を知っている人まで巻き込んで締め出せてしまう」ため、
自動化そのものを止める役はこちらに持たせています。

### 1. Turnstile のキーを作る

1. Cloudflare のダッシュボード → **Turnstile** → **Add site**
2. ドメインに Vercel のドメイン（と `localhost`）を入れる
3. **Site Key**（公開）と **Secret Key**（非公開）が発行されます

### 2. Supabase 側に Secret Key を入れる

**Authentication** → **Attack Protection** → **Enable CAPTCHA protection** を ON にし、
プロバイダに **Turnstile** を選んで Secret Key を貼ります。

> これを ON にすると、`signInAnonymously` と `signInWithOtp` は
> **captchaToken なしでは必ず失敗します**。次の手順まで済ませてから ON にしてください。

### 3. Site Key を画面側に入れる

```env
VITE_TURNSTILE_SITE_KEY=0x4AAA...
```

Vercel の環境変数にも同じものを追加して再デプロイします。
空のままなら CAPTCHA は使われず、これまでどおり動きます。

`vercel.json` の Content-Security-Policy には `challenges.cloudflare.com` を
あらかじめ許可してあるので、追加の設定は要りません。

## 外部カレンダーの取り込み（任意）

公開されている `.ics` の URL をボードに登録すると、その予定がカレンダーに重なって
表示されます。多くの配信元（Google カレンダーなど）は CORS を許可していないので、
ブラウザから直接は読めません。取得は Edge Function が中継します。

```bash
npx supabase functions deploy fetch-ics
```

> **`--no-verify-jwt` は付けません。** この中継はログイン済みの人だけに開きます。
> 検証するかどうかは `supabase/config.toml` に書いてあります。

公開した画面から使うときは、**`SITE_URL` を設定してください**。この中継が
CORS で許すオリジンになります。

```bash
npx supabase secrets set SITE_URL=https://your-app.vercel.app
```

未設定のときは `http://localhost:5173`（手元の開発サーバー）だけを許します。
以前はどこからでも許していましたが、設定し忘れたまま公開しても動いてしまい、
そのことに気づけませんでした。公開した画面で取り込みが CORS で弾かれたら、
まずここを疑ってください。

この中継には、外向きの踏み台にされないための守りが入っています。

- 取りに行けるのは **呼び出した人が見られるボードに登録済みの URL** だけ
- `http(s)` のみ。localhost・内部アドレス・予約アドレスは、名前を解決したうえで拒否
- 転送（リダイレクト）は自前で追い、各ホップで同じ検査をやり直す
- 5MB を超える応答は読まない。`BEGIN:VCALENDAR` を含まない応答は返さない
- 失敗の理由は呼び出し元に返さない（到達可否そのものが内部ネットワークの手がかりになるため）

> **登録した URL は、そのボードの参加者全員が見られます。** Google カレンダーの
> 「iCal 形式の非公開 URL」はそれ自体が合言葉なので、社外秘の予定には使わないでください
> （画面の一覧では途中まで伏せていますが、隠しているわけではありません）。

## 在席とカーソルの権限（Realtime）

付箋や予定の同期（postgres_changes）は RLS で守られますが、
**在席表示とカーソル共有（presence / broadcast）は RLS の外**にあります。
Supabase の既定では、有効なトークンさえ持っていれば任意の名前のチャンネルに
入れてしまうため、一度ボードに入って id を知った人は、あとでアクセスを
取り消されても「誰がオンラインか・表示名・見ているタブ・編集中の付箋・
マウス座標」を覗き続けられます。

`schema.sql` は `realtime.messages` にポリシーを作ってこれを塞ぎます。
画面側も該当のチャンネルを private で開きます（`src/hooks/usePresence.ts`）。
**この 2 つは対になっています。** 片方だけだと在席表示ごと動かなくなるので、
`schema.sql` を流し直さずにフロントだけ更新する、といったことはしないでください。

`schema.sql` の実行時に「在席チャンネルの権限設定をスキップしました」と出た場合は、
SQL Editor で次を実行してください。

```sql
create policy board_presence_read on realtime.messages for select to authenticated
  using (public.can_access_room(public.realtime_room_id(realtime.topic())));

create policy board_presence_write on realtime.messages for insert to authenticated
  with check (public.can_access_room(public.realtime_room_id(realtime.topic())));
```

設定できているかは次で確認できます（2 行返れば OK）。

```sql
select policyname from pg_policies
 where schemaname = 'realtime' and tablename = 'messages';
```

## ブラウザ側のエラーを見る

画面で起きた JavaScript のエラー（`window.onerror` と `unhandledrejection`）は、
`public.client_errors` に記録されます。書き込めるだけで読むポリシーはないので、
利用者どうしがお互いのエラーを覗くことはできません。読むのは SQL Editor からです。

```sql
select created_at, message, url, ua
  from public.client_errors
 order by created_at desc
 limit 50;
```

同じ内容の連投は画面側で抑えてあり、記録は 30 日で自動的に消えます
（`supabase/cron.sql` の `cleanup-client-errors`）。

> `url` はパスだけを送っています（クエリは送りません）。オーナー復帰リンク
> （`?owner=...`）がここに残らないようにするためです。

---

## 動作確認チェックリスト

**通常のウィンドウ**と**シークレットウィンドウ**を並べて開くと、
別々の利用者として動作確認できます（匿名 ID がブラウザごとに分かれるため）。

### リアルタイム同期

1. 通常ウィンドウで「リンク公開」のボードを作成し、共有リンクをシークレットウィンドウで開く
2. 付箋を貼る・動かす、ペンで線を描く、予定を追加する、TODO を追加する
3. **もう一方の画面がリロードなしで更新されること**
4. ヘッダー右上の表示が **↻ 同期中 → ✓ 保存済み** と変わること
   （開発者ツールの Network を Offline にすると **⚠ オフライン** になります）

> **オフラインのあいだの変更は保存されません。**
> 変更をためておいて後から送る仕組みは入っていないため、オフライン中の書き込みは
> 画面には出ても、リロードすると消えます。そのことをヘッダーの帯で伝えています。

### 承認制ボードの承認フロー

1. 通常ウィンドウで「承認制」のボードを作成
2. 共有リンクをシークレットウィンドウで開く → 申請フォームが出て、中身は見えない
3. 通常ウィンドウのヘッダー 👥 ボタンに赤いバッジが付く → 開いて **承認する**
4. **シークレット側がリロードなしでボードに切り替わること**
5. 「却下」した場合は入れないこと

### 全員を締め出す

1. 参加者がいる状態で、共有画面の **⛔ いったん全員を締め出す** を実行
2. 入り方が **承認制**（合言葉つきなら合言葉つき）に変わること
3. 「リンクも作り直す」を選んだ場合、**古い URL が開けなくなる**こと
4. 外された側で、新しい URL を開いても申請（または合言葉）を求められること

### 画面のテスト — 自動

DB とは別に、画面側にも 2 種類のテストがあります。

```bash
npm run lint    # ESLint。型を要求しないルールだけなので数秒で終わる
npm test        # 純粋関数（node）とコンポーネント（jsdom）
npm run test:e2e  # ブラウザで実際に触る（Playwright）
```

`npm test` は `vite.config.ts` の `test.projects` が拡張子で環境を分けます。
`*.test.ts` は node、`*.test.tsx` は jsdom です。何も要らずに走ります。
（もとは `vitest.workspace.ts` に置いていましたが、その形は Vitest 3 で非推奨・
4 で廃止されたので移しました。）

`npm run test:e2e` だけはローカルの Supabase が要ります。

```bash
npm run db:start                            # 初回はブラウザの取得も要る
npx playwright install chromium firefox webkit
npm run test:e2e
```

Chromium は全部を走らせ、Firefox と WebKit は `@smoke` を付けたものだけを走らせます
（`playwright.config.ts` の `projects`）。Chromium しか入れていないときは
`npm run test:e2e -- --project=chromium` で足ります。

Edge Function（Deno）のテストは何も要りません。Supabase も立てずに走ります。

```bash
npm run test:functions
```

つながらないときはテストを落とさず全部飛ばします（`e2e/global-setup.ts`）。
見ているのは「保存されてリロードしても残るか」「共有リンクを開いた 2 人目に
届くか」「Ctrl+Z が本当に戻すか」など、ブラウザでしか確かめられないものだけです。

### 本番へ `schema.sql` を流したあとの確認

`schema.sql` を本番のプロジェクトに流したら、**必ず 1 回だけ**これを実行してください。

```bash
# Supabase の SQL Editor に貼るか、psql から
psql -f supabase/release-smoke.sql
```

見ているのは、通知の「まとめ（digest）」でアプリ側が前提にしている 5 点だけです。

| 確認したこと | 揃っていないと |
| --- | --- |
| `notifications.folded_count` 列がある | まとめの行を作るところで落ちる |
| `kind` の制約が `digest` を許す | 同上（制約違反） |
| ふつうの通知が作れる | 通知そのものが出ない |
| 溢れた通知が `digest` の 1 行になる | 上限を超えたぶんが黙って消える |
| `folded_count` が増え、行は増えない | 「ほかに N 件」の N が出ない |

**通知が多いときにだけ落ちる**ので、揃っていなくても普段は気づけません。
気づけるのは「@メンションが届かない」という形になってからです。

pgTAP は要りません（本番には入っていないため）。使い捨てのボードを 1 つ作りますが、
**行はすべて巻き戻され、永続データは残りません**。本番でそのまま実行できます
（PostgreSQL では `nextval()` の消費だけは巻き戻りませんが、このファイルは
シーケンスを 1 つも動かしません。触るのは主キーが `uuid` の 2 テーブルだけです）。
外へ出る副作用もありません —— `schema.sql` のトリガーに `pg_net` の呼び出しは
1 つも無いので、ここから通知やメールは飛びません。

`supabase/tests/` の下に置いていないのは、`supabase test db` がその下の `.sql` を
全部 pgTAP として拾ってしまうためです（`_stub_storage.sql` と同じ理由）。

### リリースの記録を残す

本番へ流したあと、**どの commit の `schema.sql` がどの本番 DB に入っているか**を
辿れるようにしておきます。これが無いと、半年後に「この DB はどこまで入っているか」が
誰にも分からなくなります（このリポジトリには `supabase/migrations/` が無く、
DB 側に適用の記録が残らないため、なおさらです）。

`release-smoke.sql` の最後に、貼るための 1 行が出ます。

```text
schema 適用 2026-09-10 15:29 JST / commit a1b2c3d / release-smoke 5/5 OK
```

`commit` の欄だけは DB が知らないので、人が渡します。渡さなければ `未記入` と出ます。

**Supabase の SQL Editor で流すとき**は、ファイルの先頭近くにある次の行の
コメントを外して、`git rev-parse --short HEAD` の結果を貼ります。

```sql
-- set local app.commit_sha = 'a1b2c3d';
```

**`psql` から流すとき**は、ファイルを触らずにこれで済みます。

```bash
{ echo "begin; set local app.commit_sha = '$(git rev-parse --short HEAD)';"
  cat supabase/release-smoke.sql; } | psql "$DATABASE_URL"
```

`set local` はトランザクションの中でしか効かないので、先に `begin;` を送っています
（`release-smoke.sql` 側の `begin;` は「すでに開始済み」の警告が出るだけで、
同じ 1 つのトランザクションとして続き、最後の `rollback` で全部巻き戻ります）。

出た 1 行を、そのままタグの説明にします。

```bash
git tag -a schema-2026-09-10 -m "schema 適用 2026-09-10 15:29 JST / commit a1b2c3d / release-smoke 5/5 OK"
git push origin schema-2026-09-10
```

タグは commit を指しているので `git show schema-2026-09-10` からも辿れますが、
**記録の 1 行だけを見ても対応が分かる**ようにしてあります。

`まとめ` の行に「すべて通りました」と出れば終わりです。NG があれば、
`supabase/schema.sql` を流し直してからもう一度実行してください。

### 権限（RLS）が効いているか — 自動テスト

画面からの確認より先に、**DB だけで完結するテスト**を用意してあります。
`supabase/tests/rls.test.sql` に、許可されるはずのことと拒否されるはずのことを
353 件ぶん書いてあります（終了したボードへの書き込み、閲覧のみの人の編集、
変更履歴の偽造、全員締め出し、アクセスの取り消しと申し込み直し、参加期限、
リンクの作り直し、他人のボードの行を指す「この回だけ」や投票、Storage の
パスとポリシー、書いた人の名前の上書き、保存した状態からの復元など）。

```bash
# Supabase CLI で（版は package.json に固定してある）
npm run test:db

# あるいは schema.sql を流した DB へ直接
psql -U postgres -f supabase/tests/rls.test.sql
```

`1..353` と出て `not ok` が 1 件も無ければ通っています。
すべてトランザクションの中で行い、最後に巻き戻すのでデータは残りません。

> **本番のプロジェクトに流す前に、使い捨ての DB で試してください。**
> 手元で試すだけなら、Supabase の Postgres イメージだけを起動すれば足ります。
>
> ```bash
> docker run -d --name board-test -e POSTGRES_PASSWORD=postgres \
>   public.ecr.aws/supabase/postgres:17.6.1.136
> docker cp supabase/stubs/_stub_storage.sql board-test:/tmp/
> docker cp supabase/schema.sql board-test:/tmp/
> docker cp supabase/tests/rls.test.sql board-test:/tmp/
> docker exec board-test psql -U supabase_admin -d postgres -f /tmp/_stub_storage.sql
> docker exec board-test psql -U postgres -f /tmp/schema.sql
> docker exec board-test psql -U postgres -f /tmp/rls.test.sql
> ```
>
> `_stub_storage.sql` は、Storage サービスを立てずに `schema.sql` を最後まで
> 流すための足場です。本番の Supabase では要りません。
> `supabase/tests/` の外に置いてあるのは、`supabase test db` が
> その下の `.sql` を全部テストとして拾ってしまうためです（足場には
> pgTAP の plan が無いので、混ぜると必ず失敗します）。

### 押したときに自動で回す（GitHub Actions）

`.github/workflows/ci.yml` が、上の 5 つをそのまま回します。

| ジョブ | 中身 |
| --- | --- |
| `checks` | `npm run lint` / `npm run build`（`tsc --noEmit` 込み）/ `npm test` / `npm run check:functions` / `npm run test:functions` |
| `backend` | `npx supabase start` → `schema.sql` を 2 回 → `npx supabase test db` → `npm run test:e2e` |

CI で Supabase CLI を入れ直していないのは、devDependency の版をそのまま使うためです。
CLI の版の定義元は `package.json` の 1 か所だけにしてあります。

`schema.sql` を 2 回流すのは冪等の確認です。このリポジトリには
`supabase/migrations/` が無く、DB は何度でも流せる 1 本で成り立っているので、
2 回目で落ちたら `if not exists` を書き忘れたということになります。

pgTAP を Playwright より先に置いてあります。スキーマが壊れているときの
ブラウザの赤は読む価値がないので、先に落とします。

CI では `e2e/global-setup.ts` が「Supabase につながらない」を握りつぶさず
落とします（手元では飛ばします）。飛ばして緑になると、通ったのか
何も走らなかったのかが色から区別できないためです。

`actions/checkout` などの Action は、Node 24 で動く版（checkout・setup-node・
upload-artifact は v7、cache は v6）に揃えてあります。Node 20 で動く版のままだと、
GitHub が Node 24 で無理に動かし、実行のたびに警告が出ます。

### 権限（RLS）が効いているか — 画面から

承認待ちの状態のまま、シークレットウィンドウの開発者ツール Console で次を実行します
（`npm run dev` で動かしているときだけ `supabase` が Console から触れるようにしてあります）。

```js
// 承認制ボードの中身を直接読みに行ってみる
await supabase.from('notes').select('*')
await supabase.from('events').select('*')
```

いずれも **`data: []`（0 件）** が返れば、RLS が正しく効いています。
承認後に同じコマンドを実行すると、今度は中身が返ってきます。

あわせて、**申請中の画面では `notes` や `events` へのリクエストがそもそも発生しない**ことも
Network タブで確認できます（承認前は中身のテーブルを読みに行かない作りです）。

### リマインド通知

1. リマインドタブで「🔔 通知を許可」をクリック
2. 期限を 1〜2 分後に設定した TODO を作り、通知を「時刻ちょうど」にする
3. その時刻を過ぎるとブラウザ通知が出る（タブは開いたままにしてください）
4. カレンダーの予定に「5分前」を設定しても同じように通知されること
   （タブがホワイトボードのままでも通知は動きます）

## 仕組みと制約

### 利用者の識別について

このサイトにはパスワードもメールアドレスもありません。

- 表示名は「誰が書いたか」を示すためのラベルで、ブラウザの localStorage に保存されます
- 実際の権限判定には、Supabase の匿名サインインで発行される **ブラウザごとの ID** を使います

このため、次の点に注意してください。

- **別のブラウザ / 別のパソコンからは、別人として扱われます**
- ブラウザのデータを消すと、オーナー権限も失われます

対策として、ボード作成時に **オーナー復帰リンク**（`?owner=...`）が発行されます。
共有モーダルの「表示」を押すとコピーできるので、自分だけで保管しておいてください。
別のブラウザでそのリンクを開くと、オーナー権限を取り戻せます。
漏れてしまったときは、同じ場所から作り直せます（前のリンクは使えなくなります）。

同じ表示名の人が同じボードにいるときは、参加者一覧や担当の選択欄で
「ゆうき（この端末）」「ゆうき（2）」のように見分けが付くようにしています。
名前がぶつかっていない人の表示は変わりません。

オーナー以外の人も引き継ぎたい場合は、ホーム画面の 📱 から
メールアドレスを結びつけてください（任意。参加者 ID は変わらないので、
参加しているボードと作ったものはそのまま残ります）。

### セキュリティの範囲

- 承認制・合言葉つきボードの中身は、**承認されていない人からはサーバー側で読めません**（RLS）
- 「閲覧のみ」の人が中身を書き換えられないことも、サーバー側で担保しています。
  画面上のボタンを消しているだけではありません
- ただし「表示名」は自己申告なので、なりすましは防げません。
  厳密な本人確認が必要な用途には向きません
- 却下された人も再申請できます（申請の連投を防ぐ仕組みは入れていません）
- 通知の差出人名も、付箋・コメント・予定などの作成者名も、送った／書いた本人の
  表示名でサーバー側が上書きします（他人の名前を名乗って書き込むことはできません）。
  例外は「保存した状態からの復元」だけで、これは控えたときの名前を残すために、
  復元を行う関数の内側でだけ上書きを止めています
- **在席表示とカーソル共有も参加者だけに閉じています。** これは postgres_changes と
  違って RLS の外にある経路なので、`realtime.messages` にポリシーを置き、
  画面側もそのチャンネルを private で開いています。アクセスを取り消された人は、
  ボードの id を知っていても在席とカーソルを覗けません
- **画像・添付ファイルは、自分のボードのフォルダの外を指せません。** DB 側の
  制約とストレージのポリシーの両方で「パスの先頭フォルダ = ボードの id」を強制しています。
  添付は種類を絞ったうえで、署名付き URL も「必ずダウンロードになる」形で発行します
  （そうしないと、HTML を置かれたときに Supabase のドメイン上で任意の JS が動きます）
- **room_id と親の id を別々に持つ表は、複合外部キーで所属をそろえています。**
  「自分のボードの room_id」と「他人のボードの予定 id」を組み合わせた行は作れません
  （繰り返し予定の「この回だけ」は通知の送信側が予定の id だけで引くため、
  ここがずれると他人のボードの通知を止めたり乗っ取ったりできてしまいます）
- **終了したボード**（`rooms.archived`）では、作成者を含めて誰も書き込めません。
  `can_edit_room` とコメント・投票のポリシーが `room_is_open` を見ているため、
  画面を経由せず REST を直接叩いても書けません
- 参加・権限まわりの履歴（`activities` の `target_type='access'`）は、
  トリガーと RPC の内側からしか書けません。`log_access` の実行権限は
  `PUBLIC` / `anon` / `authenticated` すべてから取り上げてあるので、参加者が
  「オーナーが権限を変えた」ことにはできません（`activities` 自体にも
  INSERT のポリシーがないので、直接書き込むこともできません）
- `security definer` の関数はすべて `set search_path = ''` を付けてあります。
  テーブルも関数も `public.` / `auth.` で完全修飾しているので、`public` に
  同じ名前のものを置かれても、そちらが呼ばれることはありません
- 履歴の抑止フラグ（`app.skip_access_log`）は「全員を締め出す」処理の中だけで使い、
  対象のボードの id を入れています。他のボードの記録は落ちません。
  値を変えられるのは `pg_catalog.set_config` だけで、この関数は PostgREST が
  公開するスキーマ（`public`）にないため、外から立てる経路はありません

### 入り方（リンク公開 / 合言葉つき / 承認制）

画面では次の 3 つだけを使います。DB の `rooms.visibility`（public / private）と
`room_secrets.join_pin` の組み合わせを、この 3 つに読み替えています（`src/lib/access.ts`）。

| 入り方 | 入るのに必要なもの | DB の状態 |
| --- | --- | --- |
| 🌐 リンク公開 | URL だけ | `visibility='public'` |
| 🔑 合言葉つき | URL ＋ 合言葉 | `visibility='private'` ＋ `join_pin` あり |
| 🔒 承認制 | 作った人の承認 | `visibility='private'` ＋ `join_pin` なし |

切り替えは**共有モーダルの「入り方」だけ**で行います。ボードの設定画面は、
いまどれなのかを表示するだけです（名前と実態がずれないようにするため）。

### 共有リンクを配ったあとで締める

配ってしまったリンクにも、あとから条件を付けられます（共有モーダル → 参加の条件）。

| 設定 | できること |
| --- | --- |
| ⏳ 新しく参加できる期限 | この日時を過ぎると、新しく参加できなくなります。リンク自体が無効になるわけではありません |
| 👥 人数上限 | 参加できる人数を決められます |
| ⏸ 受付を止める | 新しい参加だけを一時的に止めます |
| 🔄 リンクを作り直す | 古い URL が開けなくなります |
| ⛔ 全員を締め出す | いまの参加者を全員外し、承認制に切り替えます（`revoke_all_members`） |
| 🔚 ボードを終了する | 中身は読めるまま、新しい書き込みを全員に対して止めます（設定画面 → ボードを終了）|

**条件を足すだけなら、いま参加している人には影響しません。**
あとから条件を足したせいで、中にいる人が締め出されることはありません。

> **リンク公開のままでは、上の条件は「読める人」を絞りません。**
> リンク公開のボードは URL を知っていれば誰でも中身を読めるため（それがサーバー側の
> 判定です）、条件が効くのは「新しく参加者として登録できるか」までです。
> 読める人を絞りたいときは、入り方を合言葉つきか承認制に変えてください。
>
> `revoke_all_members` は、この理由からサーバー側で必ず `visibility='private'` に
> 落としてから参加者を外します。リンク公開のまま外しても、URL から入り直せてしまうためです。

### 権限について

| | 見る | 付箋・予定・リマインドを変える | コメント | 投票 | 承認・設定 |
| --- | :-: | :-: | :-: | :-: | :-: |
| オーナー | ○ | ○ | ○ | ○ | ○ |
| 参加者（編集できる） | ○ | ○ | ○ | ○ | — |
| 参加者（閲覧のみ） | ○ | — | ○ | ○ | — |
| 承認待ち・未申請 | — | — | — | — | — |

リンク公開のボードでは、URL を開いた人は自動的に「編集できる参加者」になります。
限定したい場合は、入り方を合言葉つきか承認制にしてください。

### 通知の範囲

通知には 2 種類あります。

| | 動く条件 | 設定 |
| --- | --- | --- |
| ブラウザ通知 | このタブを開いている間だけ | 「🔔 通知を許可」を押すだけ |
| プッシュ通知 | タブを閉じていても届く | [プッシュ通知（任意）](#プッシュ通知任意) の設定が必要 |

どちらも、ページを開いた瞬間に過去の予定が大量に通知されないよう、
**通知時刻を大きく過ぎたものは送らない**作りにしています。

リマインドに担当者が設定されている場合、プッシュ通知はその人にだけ送られます。
担当者がいない場合と予定の通知は、参加者全員に送られます。

### 更新タブについて

「誰が何を追加・変更・削除したか」をデータベース側のトリガーで記録しています。
画面を経由しないので記録漏れがなく、あとから書き換えることもできません。

📣 更新タブでは、その記録にコメント・日程調整・参加者の動きを重ねて
1 本の時系列として表示します（これらはクライアント側で混ぜているだけで、
新しいテーブルは使っていません）。

ただし、付箋の移動やサイズ変更は記録していません（流れが埋まってしまうため）。
記録されるのは、付箋の本文・予定・リマインドの内容が実際に変わったときだけです。
`supabase/cron.sql` を設定していれば 90 日で自動的に消えます。

### ゴミ箱について

付箋・予定・やること・画像・フレーム・線・ファイル・手描き・コメントは、消しても
すぐには無くなりません（`deleted_at` を入れるだけ）。
📣 更新タブの 🗑 か、ボードの設定から **30 日以内なら戻せます**。

Ctrl+Z は自分の操作にしか効かないため、**他の人が消したものを戻せる**のはここだけです。
30 日を過ぎたものは `supabase/cron.sql` の掃除で本当に消えます。

投票・日程調整・外部カレンダーの設定は、これまでどおりその場で消えます
（戻したい場面が少ないためです）。

#### 手描きだけ、扱いが 2 つ違います

**1. ゴミ箱の行も上限に数えます。**
手描きは 1 行が重く（`points` は 120000 文字まで、上限 2500 本）、30 日ぶんを上限の
外に置くと最悪ケースが倍になります。かといって数えるだけだと、全部消したボードが
30 日ものあいだ 1 本も描けません。そこで上限 2500 は「生きている行 ＋ ゴミ箱の行」の
合計とし、天井に当たったらゴミ箱のいちばん古い行から物理削除して席を譲ります
（`tg_limit_rows_per_room` の `'yield'`）。描く手は止まらず、容量の最悪ケースは
入れる前と同じです。そのかわり手描きのゴミ箱は「30 日の保証」ではなく
「余裕があるあいだの猶予」になります。

**2. ゴミ箱の行を全員に配りません。**
ほかの表は全行を取って画面側で振り分けていますが、手描きだけは購読の時点で
`deleted_at is null` に絞っています（`useRealtimeTable` の `skipDeleted`）。
消した線の `points` まで初回読み込みに乗せると、いちばん重い表がさらに重くなるためです。
ゴミ箱の中身は、🗑 を開いたときに取りに行きます。

消しゴムは線を 1 本ずつ消すので、そのまま並べるとゴミ箱が埋まります。
続けて消したぶんは「手描き 20 本」のように 1 行へまとめます（`lib/trash.ts` の
`groupErased`。手がかりは「誰が」と「いつ」だけで、操作に印をつける列は足していません）。

#### コメントは、消す理由がモデレーションです

ほかの種類は「うっかり消した」を受け止めるためのゴミ箱ですが、コメントだけは
「この発言は置いておけない」という判断です。だから線引きを 3 つ変えています。

- **消せるのは、書いた本人とボードを作った人だけ**（ほかは編集できる人なら誰でも）。
  ポリシーは列の単位で線を引けないので、「オーナーは消せるが書き換えられない」は
  `tg_comment_trash_guard` が見ています。
- **戻せるのは、消した本人とボードを作った人だけ。** 誰が消したかを `deleted_by` に
  持ちます（サーバー側で入れるので、画面から名乗ることはできません）。ここが
  「編集できる人なら誰でも」だと、オーナーが消した発言を第三者がその場で戻せます。
- **ゴミ箱に出るのも、自分が消したぶんだけ**（オーナーには全部）。一覧に他の人が
  消した発言まで並ぶと、それ自体が「消したはずの発言を読む窓」になります。

行そのものは参加者なら誰でも `SELECT` できます。ここを絞ると、消したことが Realtime で
他の人の画面に届かず（`UPDATE` は RLS を通ります）、消した発言が相手の画面に居座ります。
すぐ消えることのほうを採りました。**画面側の目隠しであって、権限の壁ではありません。**

消した・戻したことは 📣 更新に 1 行だけ残ります（`tg_log_activity`。本文は残しません——
残すと、結局みんなに読まれてしまいます）。@メンションの通知に写った本文
（`notifications.body`）は残ります。通知はコメントの id を指していない（飛び先は付箋や
予定のほう）ので、巻き添えにする手がかりがありません。ハード削除だった頃から同じです。

### 保存した状態について

ボードの設定 → 📸 から、そのときの付箋・手描き・線・フレーム・予定・やること・画像を
丸ごと控えておけます（1 ボードにつき 10 件まで。古いものから捨てます）。

控えるのは編集できる人なら誰でもできますが、**戻せるのはボードを作った人だけ**です。
中身を丸ごと消して置き換える操作で、ゴミ箱の 30 日猶予も飛ばして消えるためです。
判定は画面ではなくサーバー側（`restore_snapshot`）で行っているので、
画面を経由せず REST を直接叩いても戻せません。

戻すと今の中身は置き換わりますが、**戻す直前の状態も自動で保存**するので、
戻し間違えても元に戻せます。復元した行は「戻した人」が作ったことになりますが、
画面に出る作成者名は控えたときのまま残します。

> 復元は 1 つのトランザクションの中で行います。作成者名を残せるのはそのためで、
> なりすまし防止の上書きを止めるフラグは、この関数の内側でしか立ちません
> （外から立てて次のリクエストへ持ち越すことはできません）。

### 描画データについて

手描きの線と図形は「1 本 = 1 行」として保存します。描いている最中は通信せず、
指を離したタイミングで 1 回だけ保存するので、通信量は抑えられています。
長く使って線が増えてきたら、ホワイトボードの「線を全消去」で整理できます。

### Undo / Redo の範囲

共同編集のため、「ボード全体を過去の状態に戻す」のではなく
**自分がこのタブで行った操作だけ**を取り消します。
他の人の操作は取り消されませんし、タブを閉じると履歴も消えます。

他の人が消したものを戻したいときは、ゴミ箱を使ってください。
ボード全体を戻したいときは「保存した状態」を使ってください。

### 繰り返し予定について

繰り返しは「元の予定 1 件」を表示時に展開する方式です。
1 回だけの変更は `event_overrides` テーブルに例外として持ち、展開のときに重ねています。

- 予定を開くと「この回だけ変更 / すべての回を変更」を選べます（既定は「この回だけ」）
- ドラッグで動かした場合も、繰り返し予定なら**その回だけ**に効きます
- 例外は「元の回の開始日」で対応づけています。そのため、すべての回の**開始日や繰り返し方**を
  変えると回の並びがずれ、既存の例外は取り消されます（保存前に確認が出ます）。
  時刻だけの変更なら例外はそのまま残ります
- **曜日の指定**（毎週 火・木 / 毎月 第 2 火曜）も持てます。
  - 週の起点は日曜で固定です。閲覧者ごとの「週の始まり」設定に合わせると、
    同じ予定が人によって違う日に出てしまい、Edge Function 側では決めようがないためです
  - 開始日が規則に合わないときは、規則に合う最初の日へ寄せます（RFC 5545）。
    金曜の予定に「毎週 火」を選ぶと、開始は次の火曜になります。寄せ先は保存前に画面に出ます
  - 曜日を**足しただけ**なら、それまでの回は動かないので例外は残ります。
    **減らした・入れ替えた**ときと、第 n 週を変えたときは取り消されます
  - 「第 5 火曜」が無い月は、丸めずに飛ばします（`.ics` の `FREQ=MONTHLY` と同じ読み方）
  - 規則は `_shared/recurrence.ts` の `normalizeRule` と `schema.sql` の
    `events_recurrence_days_check` / `events_recurrence_interval_check` の
    3 か所にあります。変えるときは全部そろえてください
  - `send-reminders` も繰り返しの 3 列（`recurrence_days` / `recurrence_week` /
    `recurrence_interval`）を読みます。取ってくる列に足し忘れても**エラーにならず、
    通知だけが違う日に飛ぶ**ので、列の並びは `src/lib/__tests__/recurrence.test.ts` で
    押さえてあります。購読 URL（`board-ics`）は別の列一覧を持っていて、
    そちらは `src/lib/__tests__/ics.test.ts` で押さえてあります
- **「n 回ごと」**（隔週、3 か月ごと）も選べます。
  - 上限は 99 です。選べる数は周期ごとに違います（毎週なら 4 週まで、毎月なら 6 か月まで）
  - **間隔を変えると回の並びが動く**ので、「この回だけ」の変更と出欠は取り消されます
  - この列より前からある予定は `recurrence_interval` が空（null）で、1（毎回）と同じ意味です。
    比べるところでは必ず 1 に読み替えているので、**開いて保存し直しただけで出欠が消えることはありません**
  - 「隔週 火・木」を木曜から始めると、最初の週は木だけ、2 週間後から火・木の両方が出ます。
    週の起点が日曜だからで、`.ics` に書き出す `WKST=SU` と同じ意味です
  - `.ics` には `INTERVAL=2` として書きます（1 のときは書きません。RFC 5545 の既定が 1 なので）
- `.ics` の書き出しでは、削除した回は `EXDATE`、変更した回は `RECURRENCE-ID` 付きの
  `VEVENT` になります。Google カレンダーなどに取り込んでも例外が保たれます。
  曜日の指定は `BYDAY=TU,TH` / `BYDAY=2TU`（序数を前に置く形。Google と Apple が
  この形で書き出すので、取り込み先の対応が広い）として書きます。
  取り込むときは `BYDAY=TU;BYSETPOS=2` の書き方も受け付けます
- **プッシュ通知（Edge Function）も例外を見ます。** `send-reminders` は
  `event_overrides` を読んでから展開するので、「この回だけ削除」した回は
  タブを閉じている端末にも届きません。「この回だけ通知あり」にした回も拾います。
  例外行は `room_id` が元の予定と一致するかを service_role 側で確かめてから使います

### カレンダーの購読 URL（任意）

ボードの予定を、読み取り専用の `.ics` として配れます。Google カレンダーや
Apple カレンダーの「URL で追加」に貼ると、あとから足した予定も追いかけてくれます。
「外部カレンダーの取り込み」の逆向きです。

```bash
npx supabase functions deploy board-ics
```

> **`--no-verify-jwt` は付けません。** JWT を検証しない設定は
> `supabase/config.toml` に書いてあります。カレンダーアプリは Authorization ヘッダを
> 付けられないので、エッジでの検証は外すしかありません。

発行はオーナーが「🔗 共有」→「📅 カレンダーの購読 URL」から行います。
デプロイしていなくてもボードの機能はすべてこれまでどおり動きます
（購読 URL を開いたときだけ失敗します）。

**この URL は、作り直すか止めるまで有効な「読み取りの権限」です。**

- URL を知っている人は、ボードに参加していなくても、合言葉や承認を通らなくても、
  予定をずっと読めます。承認制・合言葉つきのボードでも同じです
- 「全員を外す」を実行しても、この URL は止まりません。別の権限なので別の操作で切ります
  （共有画面の「作り直す」か「止める」）
- 発行・作り直し・停止は 📣 更新タブに残ります

関数側の防御（`supabase/functions/board-ics/index.ts` の冒頭にも書いてあります）:

| 項目 | 内容 |
| --- | --- |
| トークン | 32 桁の 16 進数（128bit）。形が違えば未知のトークンと同じ扱い |
| 応答の均一化 | 未知のトークン・消えたボード・内部の失敗を、すべてバイト単位で同じ 404 にする（ボードの有無を漏らさない） |
| 速度制限 | トークン別・発信元別に 1 時間 60 回。isolate ローカルなので目安。本当の防御はトークンの長さ |
| RLS の代わり | service_role は RLS を素通りするので、取得はすべて `room_id` で絞り、例外行は取得済みの予定に属するかを確かめ直す |
| キャッシュ | `Cache-Control: private, max-age=900` と `ETag`。`DTSTAMP` は「中身の最終更新」と「今日の 0:00」の遅いほうに固定してあるので、変化が無ければ 304 で返せます |

`curl` で確かめられます。

```bash
curl -i "<購読 URL>"                                   # 200 / text/calendar / ETag
curl -i -H 'If-None-Match: "<etag>"' "<購読 URL>"       # 304
curl -i "<1 桁変えた URL>"                              # 404（でたらめな URL とまったく同じ応答）
```

### 画像について

- 1 枚 5MB まで、PNG / JPEG / GIF / WebP に対応しています
- 実体は非公開バケットに置き、表示のたびに 1 時間有効の署名付き URL を発行します。
  承認制・合言葉つきボードの画像は、参加していない人からは取得できません
- 貼る・消せるのは「編集できる」人だけです（見るだけなら閲覧のみの人にもできます）
- ボード上で画像を削除しても、実ファイルは残します。行はゴミ箱に入るので、
  30 日以内ならそのまま戻せます。完全に消すのはボードを削除したときです。
  長く使って容量が気になる場合は、Supabase の Storage 画面から
  `board-images` の中を整理してください

## 構想：AI で付箋を整理する（実装の予定はありません）

**まだ実装していません。予定にも入れていません。** 入れるとしたらこの形にする、
という覚え書きです。

散らかった付箋を AI に分類させて、そのまま「やること」と「予定」に流し込めると、
ホワイトボード → やること → カレンダーという本来の流れがもう一段はっきりします。
逆に、AI を主役にしてしまうと「誰でも 5 秒で入れる軽さ」という取り柄が薄れます。
あくまで整理の手伝いに留めます。

### 置き場所

ホワイトボードのツールバーに「✨ まとめる」。選んでいる付箋（無選択なら全部）が対象です。

### やり取り

```
POST /functions/v1/summarize-board     ← Supabase Edge Function（新規）

リクエスト:
{ "room_id": "...", "notes": [{ "id": "...", "text": "..." }] }

レスポンス:
{
  "decided":   [{ "note_ids": ["..."], "text": "決まったこと" }],
  "undecided": [{ "note_ids": ["..."], "text": "まだ決まっていないこと" }],
  "todos":     [{ "note_ids": ["..."], "title": "やること",
                  "assignee_hint": "ゆうき", "due_hint": "2026-09-20" }],
  "dates":     [{ "note_ids": ["..."], "start_at": "...", "all_day": true }]
}
```

### 決めておくこと

- モデルは `claude-sonnet-5`。API キーは `supabase secrets set` に置き、
  ブラウザには絶対に出しません（`send-reminders` と同じ扱い）
- Edge Function 側で「呼んだ人がそのボードを編集できるか」を確かめます。
  クライアントの画面だけで止めても、関数を直接叩かれれば意味がありません
- ボード単位で回数を絞ります（`reminder_sends` と同じ考え方の台帳を使う）
- 返ってきた結果は**そのまま保存しない**で、いったん画面に出して選んでもらいます。
  選ばれたものだけを `src/lib/convert.ts` の `buildTodo` / `buildEvent` に渡せば、
  出自（`source_note_id`）の記録も既存の流れに乗ります
